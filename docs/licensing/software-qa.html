Nuclear software QA

How the codes behind a safety basis or license application are categorized, built, verified and accepted, under DOE directives and under the NRC with ASME NQA-1.

Drawn from public guidance and public program documents. The "Software in licensing" section reports project status and is dated; the rest is reference material.

§ 01

Software categorization (DOE & NRC)

Before any NQA-1 work, each piece of software is categorized: is it safety software, what kind of software is it, and how bad is a failure? The answer sets which of the life-cycle activities apply in full or graded form. DOE's framework is spelled out in DOE G 414.1-4 (2005, written for O 414.1C and still the main guide); the NRC's is built from Appendix B and its software regulatory guides.

DOE: three questions

1. Category

Safety system software: performs a safety function as part of an SSC cited in a DOE-approved DSA or hazard analysis.

Safety and hazard analysis and design software: classifies, designs or analyzes facilities or safety SSCs; not part of an SSC (MELCOR, MCNP, RSAC, MicroShield used for a DSA fall here).

Safety management and administrative controls software: performs a hazard control function supporting safety programs or TSRs.

2. Software type

Custom developed for the DOE application. Configurable: commercial software users can modify in limited ways (e.g. PLC logic). Acquired: COTS, freeware, firmware. Utility calculation: spreadsheets with user algorithms. Commercial design and analysis: a contractor's own software used on its own.

3. Grading level

A: failure could compromise an LCO, reduce a cited SSC's safety margin, or produce nonconservative analysis or misclassification.

B: not A, but failure could corrupt safety-management databases, mis-record hazardous exposures, or weaken defense in depth.

C: not B, but failure could cause a permit violation or affect ES&H monitoring or safe SSC operation.

Categorization steps

Inventory the software and its use

Name, version, owner, platform and exactly what each output feeds (a DSA table, a TSR surveillance, an operator display).

Decide whether it is safety software

DOE O 414.1F: at minimum, software cited in a DOE-approved safety analysis. NRC: safety-related under Appendix B if it performs or verifies a safety function, or is used in the design or analysis of safety-related SSCs.

Assign the category and software type

Using the three categories and five types above. The same code can be Level A in one use and non-safety in another, so categorize the use, not the code.

Assign the grading level from failure consequence

Ask what a wrong answer would do: nonconservative safety analysis is Level A; a bad exposure record is B; a monitoring glitch is C.

Map the work activities

Read the table for that level and type; justify every "graded" or "n/a" in writing.

Document and get approval

Record it in a safety software determination and quality level determination, then the SQA plan. DOE O 414.1F requires the graded-approach basis to be submitted to DOE for approval.

Control it and re-evaluate on change

Register in the software inventory under configuration management; re-categorize when the version, platform or use changes.

NRC software categorization with NQA-1

The NRC has no A/B/C levels. Categorization comes from the applicant's own QA program description (QAPD), which the NRC approves: software takes the safety classification of the function it serves, and that class decides how much of 10 CFR 50 Appendix B and NQA-1 Part II Subpart 2.7 applies. NRC accepts NQA-1-2017, -2019 and -2022 through RG 1.28 Rev 6.

Axis 1: what the software does

Process (plant) software: embedded in an SSC, such as digital I&C, protection logic, PLCs.

Non-process software: design and analysis codes, evaluation models, spreadsheets, databases whose output supports design or safety analysis.

Axis 2: safety class of that function

Safety-related (SR): performs or verifies a safety-related function, or analyzes a safety-related SSC. Full Appendix B and Subpart 2.7; Part 21 applies.

Non-safety-related with special treatment: the NSRST class of the LMP framework (NEI 18-04, RG 1.233) or "augmented quality"; graded controls set in the QAPD Probable.

Non-safety-related (NST): commercial practice.

Axis 3: how it was obtained

Developed under an Appendix B/NQA-1 program: Subpart 2.7 section 400 life cycle.

Acquired or commercial: qualify per Subpart 2.7 section 300, or dedicate per Subpart 2.14 with RG 1.231 / EPRI 3002002289.

NRC categorization steps

List each use

Code, version, platform and the licensing-basis document its output feeds (PSAR or FSAR chapter, a topical report, a technical specification surveillance).

Classify the function, then the software

Take the SSC classification from the licensing basis (50.2 safety-related, or SR / NSRST / NST under LMP) and give the software the same class for that use.

Pick the pedigree path

Developed under Appendix B → Subpart 2.7 section 400. Commercial or legacy → section 300 qualification or Subpart 2.14 dedication with EPRI 3002002289.

Add the use-specific layer

Evaluation models: RG 1.203 EMDAP and usually a topical report. Digital I&C: IEEE 1012 integrity level via RG 1.168, RG 1.169–1.173, IEEE 7-4.3.2 via RG 1.152, BTP 7-19 for common-cause failure.

Write it into the QAPD and SQA plan

The graded approach for NSRST and NST software must be stated in the QAPD. The NRC reviews the QAPD as a topical report or in Chapter 17 of the application.

Expect inspection

NRC vendor and construction inspections sample software records; for safety-related software, errors found later are reportable under Part 21.

§ 02

NQA-1 software life cycle

The stages an analysis code goes through under ASME NQA-1 (Part II Subpart 2.7, with Part I Requirements 3 and 11) before its results can support a DSA or PSAR. Durations are estimates for a mid-size thermal-hydraulic or neutronics code with one developer team; they vary by an order of magnitude with code size and pedigree.

2–6 weeks Speculating

Classify and grade

Safety software determination and quality level: is the code cited in a safety analysis, used for design verification, or neither? Grading sets how much of the rest applies.

1–3 months Speculating

Software QA plan

SQAP covering configuration management, V&V plan, problem reporting and corrective action, roles, and the NQA-1 edition used (the NRC accepts 2017, 2019 or 2022 under RG 1.28 Rev 6).

2–6 months Speculating

Requirements specification

SRS: functions, physics models, ranges of applicability, inputs and outputs, performance and security requirements; traceability matrix starts here.

2–6 months Speculating

Design description

SDD: model equations, numerical methods, data structures, interfaces; each requirement mapped to a design element.

continuous

Implementation under configuration control

Version control, reviewed changes, controlled baselines and release records. MOOSE shows this can run inside a CI workflow.

6–24 months Speculating

Verification and validation

Unit, regression and method-of-manufactured-solutions tests; benchmarks against experiments. For an evaluation model the NRC expects the RG 1.203 EMDAP: PIRT, assessment base, scaling, uncertainty.

2–8 weeks Speculating

Acceptance and installation testing

Test on each target platform; user documentation and training; release for use.

life of use

Operation, maintenance, retirement

Error notification to users, change control, periodic re-verification; formal retirement record.

Shortcut: commercial-grade dedication

For a code not built under NQA-1, dedication against EPRI 3002002289 (Rev 1 of 1025243), endorsed by RG 1.231, or DOE-HDBK-1230-2019 on the DOE side. Typical range 3–12 months Speculating.

Regulator acceptance: NRC

The NRC accepts methods, not codes in general: a code becomes usable through a topical report SE or the application review itself. Observed TR reviews in this tracker ran about 12–24 months Probable.

Regulator acceptance: DOE

DOE NE Order 414.1 (Aug 2025) treats software as an item; private facilities must manage safety-function software under a DOE-approved standard. DOE O 414.1F (5 Aug 2026) Part B scopes safety software as at least software cited in a DOE-approved safety analysis, with a DOE-approved graded approach. The code's acceptance rides on the NSDA Code of Record and the 45-day PDSA/DSA reviews.

§ 05

Worked example: categorizing TLECUIL

The categorization steps above, applied to my own open-source code, TLECUIL, a first-order fission surface power sizer. It is a good test case because the honest answer is "not safety software", and the program still chooses NQA-1-style controls.

StepQuestionAnswer for TLECUIL
1What is the use?First-order thermal–electrical balance for surface fission power (reactor thermal power, conversion efficiency, waste heat, radiator area, U-235 burned) for education and early concept trades. Its output is not cited in any DSA, PSAR or licensing document.
2Is it safety software?DOE: no; it is not cited in a DOE-approved safety analysis. NRC: non-safety-related; it performs no safety function and does not design a safety-related SSC.
3Category and typeNone of the three DOE safety categories. Software type: custom developed (Python and JavaScript engines).
4Grading levelBelow DOE Level C. Class E in the illustrative scheme: no safety, availability or compliance function.
5Work activities applied anywayV&V plan structured after NQA-1-2024 Subpart 2.7; 16 verification tests; JavaScript and Python engines agree to machine precision; benchmarks against four published NASA designs with a ±15% acceptance band; version control and BSD-3-Clause release on GitHub.
6Planned (v0.3)Independent human review (IR-002), verification tests VT-01 to VT-07, golden-file regression, and a first signed release record.
7Re-categorization triggerIf a TLECUIL result were ever cited in a safety analysis or used to size a safety SSC, it would move to Class B (DOE Level A analysis and design software). That would require the full Subpart 2.7 section 400 life cycle, or using a qualified code instead.

Edition note. TLECUIL's plan follows NQA-1-2024. The NRC's RG 1.28 Rev 6 endorses the 2017, 2019 and 2022 editions, so an NRC applicant would map the plan to one of those. Probable
